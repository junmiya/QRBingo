# Research: リアルタイム配信ビンゴ (v2)

**Date**: 2026-07-11 | **Spec**: [spec.md](./spec.md)

設計上の主要論点と決定事項。各項目は Decision / Rationale / Alternatives の形式。

## R-1: 同着時の順位ルール

- **Decision**: 順位は「何球目で勝利条件を満たしたか(ball index)」でサーバーが決定。同 ball index は同順位。景品数を超える同着はサーバー乱数(シードを記録し監査可能)で抽選。
- **Rationale**: 自動マーキングでは同球同着が必然的に発生する(数千人規模で数十人同着も起こる)。端末申告時刻を使うと回線速度・配信遅延で順位が変わり不公平。ball index 基準なら遅延の影響がゼロになり、遅れて届いたクレームも正しい順位に挿入できる。
- **Alternatives**: 申告時刻順(却下: 不公平)、参加順(却下: 恣意的)、先着1名のみ(却下: 配信イベントでは同着を祝う演出の方が自然)。

## R-2: 配信遅延(TV / YouTube Live)への対応

- **Decision**: 公平性は R-1 により遅延と無関係。ネタバレ(配信映像より先に手元がマークされる)対策として、ホスト設定「公開ディレイ」(0〜60秒、デフォルト0)を設け、抽選確定からプレイヤーへの公開をサーバー時刻基準で遅らせる。
- **Rationale**: YouTube Live の遅延は 5〜30 秒、TV は数秒。判定に影響しない以上、残る問題は演出のみであり、設定1つで解決できる。
- **Alternatives**: クライアント側で遅延させる(却下: 改竄可能・時計ずれ)、遅延なし固定(却下: 配信で番組進行より先に結果が漏れる)。

## R-3: 当選者との連絡手段

- **Decision**: メールアドレスは収集しない。当選者に推測困難な「当選コード」を表示し、主催者ダッシュボードの一覧と照合して主催者自身のチャネル(応募フォーム・DM等)で受け渡す。
- **Rationale**: (a) PII を持たないことで個人情報保護法対応(同意・保管・削除体制)が不要になる。(b) 「当選したのでメールを入力」という UI はフィッシングと外見が同一で視聴者に警戒される。(c) メールが必要な主催者は外部フォームへのリンクを当選画面に置けば足りる。
- **Alternatives**: アプリ内でメール収集(却下: 法対応コストと詐欺類似 UX)、アプリ内チャット(却下: モデレーション負担、Out of Scope)。

## R-4: バックエンド基盤

- **Decision**: Firebase — Firestore(リアルタイム配信)+ Cloud Functions(抽選・検証・順位確定)+ Anonymous Auth(1ブラウザ1UID)+ App Check(bot 抑止)。
- **Rationale**: ビンゴは通信頻度が低い(20〜30秒に1回、小さな数値)ため Firestore の onSnapshot と相性が良い。スパイク(QRがTVに映った瞬間の一斉参加)にマネージドで耐え、運用ゼロ。概算: 1万人×75球 ≈ 75万リード ≈ 数十円。
- **Alternatives**:
  - Supabase(却下: Realtime 同時接続の無料枠が小さくスパイクに不向き)
  - 自前 Node + WebSocket(却下: スケールと運用を自前で負う。将来の移植先としては可)
- **Note**: 判定は「クレーム方式」— クライアントが成立を検知して申告し、Functions が該当カードのみ検証する。全カード総当たりを避けることで抽選ごとの計算量を O(クレーム数) に抑える。

## R-5: 多重参加・不正対策

- **Decision**: Anonymous Auth で 1 UID = 1 ゲーム 1 カード。App Check でヘッドレス bot を抑止。カードはシードのみサーバー発行・グリッドはサーバー再計算で検証(クライアントのグリッド申告を信用しない)。「1人1回」の厳密な本人確認は行わない(割り切り)。
- **Rationale**: 公開QRである以上、完全な本人一意性は認証なしでは不可能。被害の大きい不正(改竄クレーム・大量bot)を優先的に潰す。

## R-6: セッション継続

- **Decision**: Firebase Anonymous Auth の永続化(IndexedDB)+ Firestore 上のカード紐付け。Cookie は使わない。別端末からの復帰は非対応と明記。
- **Rationale**: 要件の「Cookieで継続」を上位互換で満たす。IndexedDB は Cookie より消えにくく、サーバー側にカードがあるため localStorage 消失でも復元可能。

## R-7: カードの一意性とパターン数

- **Decision**: カードパターン総数は 360,360⁴ × 32,760 ≈ 5.52×10²⁶。一意性保証はグリッドの正規化ハッシュを Firestore に置き、発行時に重複チェック(トランザクション)。「同一カードあり」オプションはこのチェックを省略する性能フラグ。
- **Rationale**: パターン数が事実上無限のため、一意性が定員を制約することはない。定員は純粋に運用設定。

## R-8: ニックネーム

- **Decision**: 参加時(カード発行前)に必須入力。1〜12文字。NGワードフィルタ(クライアント+サーバー両方)+ ホストの「非表示」ボタン。
- **Rationale**: ビンゴ成立の瞬間に入力させると順位確定と干渉し UX が悪い。ランキングが放送に映る前提なのでモデレーション手段は必須。
